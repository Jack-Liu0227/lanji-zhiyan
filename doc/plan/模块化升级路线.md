# 1.0 模块化升级路线

## 目标

以本仓 1.1.4 为行为基线，保留现有 Python + 本地网页桌面形态和数据；把“模块”逐步变成可独立维护、测试、升级，并由宿主按配置组合的功能包。此路线不迁移到 Electron，也不直接搬入 2.0 的功能。

## 模块边界

- **宿主**：窗口、HTTP/SSE、模块装配、全局权限与启动；不承载具体科研业务。
- **共享核心**：项目/数据库访问契约、文件安全、模型调用、任务状态与事件；模块只能通过明确接口使用。
- **功能模块**：一个模块自带 `manifest`、后端服务/API、前端入口、自己的数据迁移和测试；模块之间不直接导入对方内部实现。
- **连接器**：Zotero、Obsidian、RSS、邮箱等外部系统适配器，由模块通过共享连接器接口调用。
- **工作流组合**：工作流只编排模块暴露的能力，不复制模块业务逻辑。

## 执行阶段

1. **建立装配边界（本轮）**：把现有 API 扩展路由改为有序注册表；保持现有端点、顺序、权限和响应逻辑不变。
2. **定义模块契约（本轮）**：增加稳定模块 ID、语义版本、宿主能力依赖与启用标记；注册时检查版本/依赖，保持静态内置，不急着做热插拔。
3. **试迁 easyScholar API（本轮进行中）**：期刊分区端点已从综合业务路由拆出为独立路由模块；下一步还要把设置界面从共享 integrations view 拆出来，并验证关闭模块时 UI/API 一致。
4. **按依赖逐块迁移**：再迁连接器型功能、项目资料型功能、任务/团队/工作流等高耦合模块；先抽共享核心契约，避免一次性重写。
5. **启用组合与独立发布**：模块版本/依赖检查、配置启停、迁移回滚策略和模块包升级流程稳定后，再开放模块组合及独立分发。

## 当前进度与边界

- 已完成：有序 API 注册表、稳定模块 ID、版本格式校验、宿主能力依赖校验、静态启用标记；原路由顺序与响应逻辑保留。
- 进行中：easyScholar 后端路由已独立，前端设置仍嵌在共享集成页；因此目前不能称作完整可独立升级模块。
- 未做：用户可配置启停、模块包安装/升级、模块专属迁移和 UI 动态装配。完成 easyScholar 端到端试迁后再实现这些能力，避免空搭插件系统。

## 验收门槛

- 未启用模块的路由和界面入口不可见，相关数据不被删除。
- 模块可独立运行自己的测试；跨模块依赖由宿主契约注入。
- 更新一个模块不会要求重写其他模块内部代码；数据库变更可识别、可备份、失败不丢数据。
- 现有功能回归测试保持通过，旧数据库可直接升级。

## 当前边界

注册表已有静态模块元数据和路由装配能力，但宿主仍在代码中一次性注册全部模块；目前没有从配置装配、UI 启停、独立包安装升级，也未把模块的数据迁移独立出来。下一步先完成 easyScholar 前端设置的模块归属和启停一致性，再决定推广范围。
