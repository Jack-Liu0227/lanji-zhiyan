# 翻译提速 + 荧光笔 升级（已落地，附实测）

日期：2026-10-21 ｜ 对象：research-workbench 论文翻译（papertran.py / paper-translation.js / workflow-view.js）

## 一、翻译为什么慢：真因是 thinking 吃满了 max_tokens

babeldoc 的 OpenAI 翻译器把 `max_tokens` 硬编码成 2048（site-packages/babeldoc/translator/translator.py:322）。
当前激活模型 deepseek-v4-flash 默认开 thinking，**reasoning token 计入这 2048 预算**，正文 JSON 被挤空
→ babeldoc 抛 `Expecting value: line 1 column 1 (char 0)` → 整个 batch 退回「逐段单句翻译」，
每段都单独过 QPS 限流器。

历史日志 936cd18f.log 的算术正好对上：`Total: 15, Successful: 1, Fallback: 14`、
`Translate Paragraphs 245 段 / 1:55`，而 qps=QPS_TOTAL(8)/段数(3)=2 → 245/2≈122s。实测 115s，吻合。

### 实测 A/B/C（同一 PDF、同 4 页、同模型，各跑一遍真 babeldoc）

| 配置 | 总耗时 | 翻译阶段 | batch 成功/全量 |
|---|---|---|---|
| A 现状 | 65s | 44s | 1/31（30 段 fallback） |
| B 只关 thinking | 35s | 14s | 30/31 |
| C 关 thinking + json mode + qps=8 | **25s** | **4s** | **31/31** |

单次请求实测（DeepSeek 直连）：
- 默认：completion 270 token，其中 reasoning 206（76% 白烧），content 119 字
- thinking 关：completion 63 token，content 115 字，快 30%

### 38 页整篇对照（最终取值依据）

| 配置 | 端到端 | 版式识别 | 翻译 |
|---|---|---|---|
| 原参数（3 段 + 第 1 页单独 = 4 进程并行） | **231s** | 73s | 115s |
| 新参数单段（qps8） | 101s | 29s | 38s |
| 新参数（2-38 页一段，qps16） | **83s** | 23s | 20s |

**版式识别是段并行的负收益**：babeldoc 每个进程按满核跑 ONNX，4 段并行时 13 页要 73s，
单进程 38 页只要 29s —— 所以段数从 3 降到 1，`_plan` 变成「第 1 页单跑 + 其余一整段」，
第一页照样先出来。落地后 38 页端到端约 **85s**（原 231s，2.7×）。

### 改动（papertran.py）

```python
QPS_TOTAL = 16          # 原 8
CHUNK_PARALLEL = 2      # 原 3
CHUNK_MAX = 1           # 原 3 —— 段并行拖慢版式识别
```
```python
cmd = BABELDOC_CMD + [...
      "--enable-json-mode-if-requested",                 # batch 输出严格 JSON，fallback 归零
      *(["--openai-thinking", "disabled"] if "deepseek" in cfg["base"].lower() or "deepseek" in cfg["model"].lower() else []),
      ...]
```
`--openai-thinking disabled` 只对 deepseek 系列发（其他 provider 不认这个 extra_body 时可能 400）。

## 二、荧光笔为什么迟钝

### 1. 论文翻译页（PDF）：彻底失效，不是迟钝

`paper-translation.js:317` 调 `trHlSave()`，但这个函数**全仓没有定义**（grep 只有两处调用）。
划完必抛 ReferenceError，在 `trHlSave(); trPaintHls(...)` 这一行就断掉 → 不上色、不存盘。

修：补 8 行（localStorage 兜底 + 400ms 防抖 POST /api/tr/hl）。

### 2. 每一处标注 = 几十个 div

`trHlOnMouseUp` 把 `sel.getRangeAt(0).getClientRects()` 逐条 push，而文字层是**逐词 span**。
划一个 5 行段落 → 生成 ~60 条记录、60 个高亮 div，词间还有缝，视觉上是断续小方块。
数据量、绘制、保存全部被放大几十倍。

修：rect 按行合并（相邻 y 差 < 半行高 → 并成一个矩形），60 条 → 5 条。

### 3. 文字层要等 6.65s 才出现

`/api/pdftext` 用 pdfplumber 抽全篇词坐标。实测这份 39 页 PDF：**23864 词 / 6.65 秒**（pdfplumber）。
这 6.65 秒里页面上没有任何可选文字，拖选当然没反应。

换 pymupdf 能到 0.084s（79×），但**pymupdf 是 AGPL-3.0**，而 pdfio.py 开头明确写着
「只用宽松许可的实现：pypdf(BSD-3)、pdfplumber(MIT)」—— 不能为了 6 秒引一个 AGPL 依赖。

更省的做法：**文字层根本不用后端**。前端已经在用 pdf.js 渲染，`page.getTextContent()`
本地就能给出每个字符串的 transform + width，直接铺 span，零请求、零等待、零许可问题，
而且坐标与渲染同源（比 pdfplumber 更贴）。同时删掉 trWords 的异步链，净减代码。

### 4. 工作流审查步的荧光笔：跨标签就静默失败

`workflow-view.js:272` 用 `range.surroundContents(mk)`，选中的一段文字只要跨了
`<b>` / `<code>` / `<a>` 等元素就抛 `HierarchyRequestError`，被 `catch(_){ return }` 吃掉 ——
表现就是「有时候能划，有时候划了没反应」。
改 `mk.appendChild(r.extractContents()); r.insertNode(mk);` 即可包任意结构。
